# Where the Noted cohort data comes from

Chapters 5 and 6 investigate the same fifty users. Chapter 5 reads what the
product wrote down; Chapter 6 reads what the product observed happening. Both
halves are vendored here so every printed result can be reproduced without a
Convex deployment, an Amplitude account, or a network connection.

Build the database with:

    python companion/sql/noted/load_noted.py

## The two snapshots

| File | What it is | Generated by | Seed |
| --- | --- | --- | --- |
| `upstream/noted_cohort_rows.json` | Convex product tables, expanded | `scripts/seed-convex.mjs` via `cohort-fixture.mjs` | 20260518 |
| `upstream/noted_cohort_events.json` | Amplitude event stream, 2,932 events in 12 types | `scripts/seed-amplitude.mjs` | 20260519, derived from the above |
| `upstream/cohort-sample-data.json` | The fixture both expand from | — | 20260518 |
| `upstream/amplitude-plan.json` | Cohort window and dashboard plan | — | — |

Source repository: `avidx-app/noted-main`. The rows snapshot was captured at
commit `985ad95`; the event snapshot from the seeder on the
`seed/reproducible-amplitude-cohort` branch, which made the stream reproducible
and is described below.

**One edit to the raw seeder output.** Two event types belonging to an internal
page outside the product's core workflow are removed from the snapshot. They are
legitimate product events and remain in the seeder; they are simply out of scope
for what these chapters teach. Nothing else is filtered, and no row in any other
table or event type is altered.

The event window is **2026-01-01 to 2026-01-30**, fixed by `--anchor 2026-01-30`
rather than taken from the system clock, so regenerating the snapshot next month
reproduces it exactly rather than sliding the window forward. Regenerate with:

    node scripts/seed-amplitude.mjs --anchor 2026-01-30 --out noted_cohort_events.json

## The data is synthetic, and shaped rather than found

The fixture declares an `expectedPattern` for each insight, so the cohort was
designed to contain the patterns the chapters investigate. What the reader gets
is not discovery in the wild but **reproducibility**: the same seed returns the
same rows, so every query in the book can be re-run and every printed number
re-derived. The chapters say so, and neither presents these figures as
production measurements.

## Three things the data does on purpose

**There is no users table in the product.** Noted's Convex schema has none —
identity lives in the auth provider, so `userId` is an opaque string with nothing
to join to. The `users` table in this database is a *derived* analytics
dimension, assembled here because a real team would have to assemble it too.

**The event stream does not reconcile with the product tables.** Roughly one user
in eight runs a blocker or strict privacy mode and is close to invisible to
analytics while fully active in the product; everyone else loses the occasional
beacon when a tab closes before it flushes. The stream therefore delivers about
79–85% of what the tables recorded:

| Measure | Product tables | Event stream | Delivered |
| --- | --- | --- | --- |
| Documents created | 243 | 203 | 83.5% |
| Documents published (net of withdrawals) | 35 | 28 | 80.0% |
| Documents archived | 28 | 22 | 78.6% |
| Coworker messages | 2,895 | 2,444 | 84.4% |

A seed that reconciled perfectly would teach a reconciliation no real product
ever gets. `reconcile_sources()` in `load_noted.py` pins both sides of this
table, so a regenerated snapshot cannot quietly change a number the book has
printed, and fails if the stream ever *exceeds* the tables — which would mean
double-counting rather than loss.

**`coworker_messages` is a count bucket, not one row per message.** The product
records a running total per user; per-message grain lives only in the event
stream. The two are different measurements of the same behaviour and the book
never prints them as though they were the same number.

## Persona labels are labels

Every user carries a `persona` — `power_users`, `casual_users`, `churned_users`,
`trial_users` — encoded in the seeded `userId`. These are labels somebody
recorded, not behaviours anybody measured, and the event stream does not always
agree with them. That disagreement is deliberate and is the subject of a
Chapter 6 query rather than a defect to be corrected here.
